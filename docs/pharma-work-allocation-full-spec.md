## Phase 2 — Tenant Provisioning

### Files (5)

```
apps/api/prisma/tenant-schema.prisma          (stub for now, filled in Phase 4)
apps/api/src/modules/tenant-provisioning/tenant-provisioning.module.ts
apps/api/src/modules/tenant-provisioning/tenant-provisioning.service.ts
apps/api/src/prisma/prisma-client-factory.service.ts
```

(4 files)

### Functions

**`tenant-provisioning.service.ts`**

- `provisionTenant(companyId: string)` — orchestrates the full provisioning flow: creates the new DB (via Neon API call or `CREATE DATABASE` if same-project databases), runs tenant migrations against it, saves the connection string.
- `createTenantDatabase(companyId: string)` — the actual DB-creation call (isolated so it's swappable/testable independently of migration logic).
- `runTenantMigrations(dbUrl: string)` — shells out to `prisma migrate deploy --schema=tenant-schema.prisma` with `DATABASE_URL` set to the new tenant's URL.
- `saveTenantConnection(companyId: string, dbUrl: string)` — writes/updates the `TenantConnection` row, sets `provisioned = true`.

**`prisma-client-factory.service.ts`**

- `getClientForTenant(dbUrl: string)` — returns a cached `PrismaClient` instance scoped to that tenant's DB (caches by `dbUrl` so you're not opening a new connection pool per request).
- `clearCache(dbUrl: string)` — evicts a cached client (useful if a tenant DB URL ever changes).

### Wiring change

- `companies.service.ts` gains one more function: `createCompanyAndProvision(dto)` — calls `createCompany()` then `tenantProvisioningService.provisionTenant()`.

### Test

- Provision two companies, confirm two separate DBs exist in Neon's dashboard.
- Insert a row into tenant A via `getClientForTenant(tenantA.dbUrl)`, confirm it's absent when querying tenant B's client.

### Files (8)

```
apps/api/src/modules/auth/auth.module.ts

apps/api/src/common/decorators/current-user.decorator.ts

```

### Functions

**`auth.service.ts`**

- `login(dto: LoginDto)` — looks up which tenant the email belongs to, verifies password, returns a signed JWT.
- `findUserTenant(email: string)` — control-plane lookup: which company/tenant DB does this email belong to.
- `validateCredentials(tenantClient, email, password)` — fetches the user from the tenant DB, compares password hash.
- `signToken(payload: { userId, companyId, role })` — issues the JWT.

**`auth.controller.ts`**

- `login(@Body() dto)` — `POST /auth/login`

**`jwt.strategy.ts`**

- `validate(payload)` — Passport hook that runs on every authenticated request; returns the decoded `{ userId, companyId, role }` to attach to `req.user`.

**`jwt-auth.guard.ts`**

- No custom functions — extends Passport's `AuthGuard('jwt')`.

**`current-user.decorator.ts`**

- `CurrentUser` — param decorator that pulls `req.user` into controller method arguments.

**`tenant-context.interceptor.ts`**

- `intercept(context, next)` — reads `companyId` from `req.user`, looks up the tenant's `dbUrl` via `TenantConnection`, calls `prismaClientFactory.getClientForTenant()`, attaches the resulting client to the request as `req.tenantPrisma` so every downstream service can use it.

### Test

- Seed one user in Tenant A's DB, one in Tenant B's DB.
- Log in as each, hit a protected route, confirm `req.tenantPrisma` resolves to the correct DB for each — verify via a query that only returns that tenant's data.

## How to Use This

Work top to bottom, phase by phase. Within a phase, create files in the order listed (module → controller → service → DTOs) — Nest's dependency injection means the service usually needs to exist before the controller compiles cleanly against it. Don't start a phase's UI/mobile work until its API phase's test checklist passes.
